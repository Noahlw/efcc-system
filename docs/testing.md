# Testing workflow

Authority: [Spec #66](https://github.com/Noahlw/efcc-system/issues/66), tickets #67–85, [CI follow-up #182](https://github.com/Noahlw/efcc-system/issues/182) and the [confirmed test-gate amendment](testing-foundation/test-gate-advisory.md). The amendment changes execution placement, not required delivery coverage; [#206](https://github.com/Noahlw/efcc-system/issues/206) owns safe progress only. Historical receipts qualify their recorded source, not later edits. Accepted product visuals and the Design Book are unchanged.

For the shared PR body, flexible UI Preview, evidence and reviewer responsibilities, see the [Pull Request Delivery Contract](agents/pull-request-contract.md).

## Toolchain and commands

Use Node **24.21.0**, pnpm **10.33.2**, the checked-in lockfile and, for local Native checks, installed Playwright browsers. Bootstrap with `pnpm install --frozen-lockfile --prefer-offline`; missing locked packages may be downloaded. Install scripts are not globally disabled.

GitHub PR and main-push `checks` are light: actionlint, format/lint/runtime-boundary check, typecheck and one unit-coverage run. PR CI validates the actual event base/head/tested merge identities and exported source tree. It still validates source selection, including unknown paths, but does not install browsers, build the app, execute Native, replay base coverage or run mutation. There is no full-test GitHub backup workflow. CodeQL, Dependency Review and existing secret protections retain their separate responsibilities. The stable `checks` context remains subject to the existing ruleset; a green CI result proves only these light checks.

Every commit requires exact-staged formatting, lint/runtime-boundary checks, complete project typecheck and fast contracts. Saving a commit does not establish delivery readiness. Before Ready or merge, every PR, including Dependabot, bots and web-created changes, needs complete agent-run local qualification of its actual candidate against the current base. Changed source or base requires refreshed evidence. Hooks and local readiness validation do not prevent direct GitHub UI actions; GitHub does not attest local Native execution. This remains an explicit author/reviewer delivery responsibility. All Owner/release gates remain separate.

CI and complete qualification use one `pnpm test:coverage` execution instead of running ordinary units and coverage twice. Commit and development feedback use the fast class without coverage. The fast config excludes only the expensive Native-selection, process-lifecycle, snapshot-gate and qualification integration suites; they remain in the default and coverage suites. Uncertain source/config/subprocess relationships fall back to the whole fast class; zero import-graph matches are not proof of safety. Coverage includes every executable `src` `.ts` and `.tsx` file, including unimported files, and excludes `.d.ts` declarations. No percentage threshold is enforced.

Coverage inventory compares physical source paths so a symlinked checkout and its report refer to the same files. Missing files, duplicate physical entries and incomplete source coverage remain blocking.

Base-worktree Git commands use the clean test environment, without the submitting hook’s `GIT_INDEX_FILE` or other repository overrides. The real hook index remains authoritative for staged export and drift checks.

Applicable qualification compares candidate coverage with its merge base against the explicit PR base, using the base's lockfile/dependencies and the candidate's pinned measurement overlay. This advisory replay runs after required Native feedback, not during commits or development affected checks. The ordinary Vitest config must be byte-identical; incompatible or unreproducible measurement is `INCOMPARABLE`, with no delta. Missing candidate coverage remains blocking; comparison failure is advisory, but cleanup failure blocks. Private `coverage-summary.json` records aggregate metrics and base/head/tree; an uncommitted tested tree has `tested: null`, not an invented tested commit.

CI records its actual tested commit and `not-run-in-ci` base comparison, publishing candidate-only coverage to the Actions summary. Local base comparison belongs in PR Evidence, with source identities and limits. Raw coverage reports remain ignored and are not uploaded or written to PR comments. Per-file coverage does not classify changed-source groups or assign test ownership.

Direct native commands require an owned clean checkout without local vars; the Git gate is the normal route from a developer checkout. It exports only the authoritative Git tree to a private disposable source, validates privacy, installs that snapshot's locked dependencies/config and executes its own policy. Do not move/delete personal `.dev.vars` or `.wrangler` to run tests. Tests do not invoke `db:reset:local`. That explicit destructive developer command and `db:migrate:local` operate on developer D1 and require separate authorization; they are not test setup.

Feature projects default to two workers on every machine, including CI. An optional machine-only file at `~/.config/efcc/feature-workers` contains a positive integer to override local feature concurrency; for example, `4` selects four workers on a separately verified host. The file is outside Git and applies to direct feature commands and the immutable local gate without shell setup. CI ignores the machine file. The existing `PLAYWRIGHT_WORKERS` environment override remains available for direct diagnostics; the gate continues to sanitize its environment. Native compatibility retains its existing default of two workers; causal, dev and lifecycle projects retain their serial worker settings. Worker selection does not relax isolation, zero-retry or execution-completeness checks; the Playwright JSON receipts record the resolved worker count.

## Mutation pilot

`pnpm test:mutation` uses Stryker against only `src/features/account/identity-validation.ts` and `tests/shared/account/application-contract.test.ts`. Its isolated Vitest config retains aliases and selects that contract file. Complete local qualification runs the pilot only under the existing source/direct-test/config/toolchain/full-qualification policy; it no longer runs during commits or development affected checks. Scope and score policy are unchanged. It does not run Native per mutant. The runner validates schema and exact scope, retaining private source-bearing JSON and sanitized aggregate `mutation-summary.json` metrics. Uncommitted candidates have `tested: null`; CI does not run mutation. Do not upload raw mutant source, set a score threshold, exclude survivors to raise the score, or treat survivors/uncovered mutants as confirmed product defects. Setup failures and timeouts remain distinct from test outcomes.

The initial implementation pilot produced 125 mutants in 13 seconds: 25 killed, 91 survived, 9 with no coverage, 0 timed out and 0 errors. Stryker reported a 20.00% total mutation score and 21.55% for covered mutants. The uncovered mutants were in username validation; survivor examples also showed email and phone alternatives the selected contract suite did not distinguish. This is a narrow test-strength signal, not a whole-repository quality baseline or evidence that the current production behavior is wrong. The machine-readable result is written to ignored `coverage/mutation/mutation.json` and is regenerated by each run.

Stryker 10.0.0 currently requires a TypeScript compiler API that the repository's TypeScript 7.0.2 no longer exposes. A pnpm `packageExtensions` entry gives only `@stryker-mutator/core@10.0.0` its own TypeScript 6.0.3 dependency; the application and root typecheck continue to resolve TypeScript 7.0.2. The runner is named explicitly in Stryker's `plugins` list because strict pnpm dependency links do not make a sibling runner discoverable through Stryker's package-local wildcard search. Revisit both tool-only compatibility settings when a Stryker release supports the root TypeScript API and resolves the runner correctly under pnpm; verify the real mutation run before removing them.

## Gate, selection and evidence

One Husky pre-commit uses native lint-staged formatting followed by exact-staged project checks and fast contracts. Native lint-staged owns partial-hunk hiding/restoration, backup/revert and formatter staging; no custom stash or generated-output auto-staging is added. Index drift fails closed. Unknown paths/renames/deletions require a mapping or explicit full-selection intent, never a silent fast-only delivery exemption. One source-area/risk map retains required claim tags and engine intent. Commit execution does not perform Native collection. Whenever Native executes, unfiltered definitions and the complete runtime/engine matrix are validated before scoped execution. The collection project never executes. CLI grep intersects transport filters, projects select mobile scope, and discovery/execution must match with no skip/retry. Shared auth/DB changes retain independent semantic boundaries, HTTP runs once, and engine-sensitive cases retain required mobile projects.

The runner reports immutable source/base identity, selection, toolchain and safe aggregates; raw runtime output, Native IDs, logs/traces and private evidence remain private. Preserve the first failure; neither CI nor a later retry waives it. Never disable Husky, use `--no-verify`, skip required tests or weaken assertions, formatting, types or CI. Commit-check failures block saving the commit; incomplete/failed qualification blocks local readiness and delivery, not ordinary development checkpoints. No pre-push gate or cached-pass service exists.

Avoid redundant validation: during implementation use changed-path checks and distinct native counterexamples. Freeze the contracted candidate before the complete qualification. Do not chain full `qualify`, `affected` and `staged --full` merely because they are different aliases. Staged fidelity, selection, privacy and interruption have their own targeted counterexamples; passing results are never reusable cache artifacts.

Owned process-group cleanup is complete only after native signal zero confirms that the group is absent. A permission error is not evidence of absence. If absence cannot be confirmed within the cleanup bound, the command fails; owned descendants/listeners cannot be silently abandoned. Historical deleted-path mappings classify PR-base changes; their strings are not active legacy implementations. [#84](https://github.com/Noahlw/efcc-system/issues/84#issuecomment-6165625298) retains the detailed retirement/equivalence history.

The runtime boundary check uses the installed TypeScript compiler API to discover current `src` client roots and resolve their local runtime imports, including aliases and re-exports. `pnpm check` and Vite configuration both enforce it. Type-only server contracts remain valid; server composition roots are not client roots, and local cycles are reported rather than rejected. `node scripts/runtime-boundaries.ts` emits the current source/client/server inventory and any forbidden dependency traces, so added, renamed and removed owners are discovered without a handwritten root list. This is a bounded local-source check; actual client builds still qualify package dependencies and framework transforms.

Module resolution compares original compiler filenames rather than case-folded symbol paths. Coverage inventory resolves physical source paths so symlinked checkouts neither omit modules nor count aliases twice.

### Early development checks and readiness

Run affected Native checks early for authorization, SQL atomicity, Session, recovery and UI-journey changes. Changes to runner/bootstrap/discovery/lifecycle owners also require their relevant retained integration suites during development; invoke the corresponding files through `pnpm exec vitest run`, not the fast command. Do not wait for final qualification to discover these boundary failures.

Freeze source before one complete `pnpm test:qualify --base <actual-PR-base>`. Its private `qualification-summary.json` is written only after required reports/stages, process cleanup, source disposal and fresh source/base validation. The local `ready` command requires that receipt and underlying unchanged reports, complete command/selection evidence, current tree, current target-base tip and merge-base, and the pinned toolchain. Missing, failed, partial, stale or unconfirmed-cleanup evidence is rejected. Staged/affected/CI/progress output cannot substitute for this receipt. A new commit with an identical tested tree does not retroactively change `tested: null` into a tested commit. Local receipt validation is not a signed attestation or protection against an author fabricating evidence; independent review remains necessary.

### Safe live progress

The existing runner emits append-only `EFCC progress` lines in terminals, CI and non-TTY OMP jobs. Watch the running job's output; no TTY, animation or raw-log access is required. Named stages show start/end/failure and elapsed wall time; unit and Native stages show completed cases and failures separately. Native totals use the actual selected project×case matrix. Units omit an unreliable denominator; retries do not inflate case completion. A heartbeat means the observation owner is alive, not that the child is making useful progress.

Progress comes from bounded private structured reporter events, not scraped stdout/stderr. Public fields are allowlisted stages, known projects, numeric counters/time and safe outcomes. Test identities, paths, payloads, errors, credentials and traces are not progress fields; detailed per-test timing stays in private native reports. Missing, malformed or stale reporter data is labelled unavailable/stale, never guessed. `command-passed` reports only the wrapped operation's result; only complete authoritative receipts establish qualification. Command failure/timeout/interruption and cleanup retain their blocking semantics. Reporter-channel files are removed at stage end; no hosted telemetry or persistent progress store is added.

For runs started with `CI=true`, Vitest also retains `unit-results.json` inside the same private evidence directory, including failed cases and per-case durations. Raw child output and report-path announcements are suppressed in this mode. Without `CI=true`, the gate does not request this additional JSON reporter, so it adds no report-path announcement or path-bearing failure argument. Do not upload the report or treat it as a qualification receipt. Hosted CI does not publish it, so it is unavailable after runner teardown. A failed run may leave this diagnostic report without any terminal qualification summary.

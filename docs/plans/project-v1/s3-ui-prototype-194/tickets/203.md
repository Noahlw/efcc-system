## What to build

An Admin opens their own Account exit task, defaults to Member or deliberately chooses Staff, confirms the final danger action and signs in afresh after authoritative success. The last effective Admin cannot leave, and a lost response remains honest uncertainty.

## Acceptance criteria

- [ ] Account self-exit defaults Member and supports explicit Staff; adding another Admin remains a separate journey.
- [ ] Concurrent last-effective-Admin exits cannot remove the final effective Admin; real native failures leave required effects uncommitted.
- [ ] Confirmed exit revokes every actor Session including initiating Session and requires fresh sign-in; no old management screen/labels survive.
- [ ] Final exit uses danger with clear consequences and accessible confirmation; valid proof is reused and expired proof requires explicit final action.
- [ ] Lost response after possible revocation is UNKNOWN with no post-revocation receipt exception, replacement command or false success/failure claim.

## Implementation method

1. Adapt the existing own Admin step-down task under Account using the #196 frame/proof composition. Member is default; Staff is explicit. Explain consequences in-task. This is an explicit command task, so do not require a fake dirty identity change merely to make the final exit action available. Final own-exit confirmation uses danger; other Back/Reset/cancel controls keep quiet/secondary semantics.
2. Reuse the existing SQL-time last-effective-Admin/native race guard and all-actor-Session revocation including initiating Session. Do not replace DB guard with a stale UI count, and do not relax existing credentials/effective-Admin definition. No peer Admin removal, fallback role switch or migration of bootstrap/recovery into UI.
3. Confirmed success proceeds to fresh sign-in and then normal independently permitted navigation. If commit may have happened but the response is lost, render UNKNOWN. Session revocation does not create a post-revocation receipt-reading exception; fresh sign-in/current role/Inbox or receipt absence do not retrospectively prove that operation succeeded or failed. Preserve only permitted opaque original-operation recovery metadata; never protected old labels/drafts or new-command retry.

## What to build

An authorized Admin/Role Assigner edits several known Department Manager duties for one person, reviews the explicit net set and saves the set all-or-none. A definite conflict or unknown response cannot leave partial role changes or create a replacement command.

## Acceptance criteria

- [ ] One Save grants/withdraws several known DM assignments for one permitted person with exactly the required atomic effects and one original-operation settlement.
- [ ] Grant/withdraw eligibility differs correctly; exact withdrawal witness and SQL-time authority survive races; protected/out-of-scope requests fail with no write.
- [ ] Unknown or unloaded scopes do not enter the command; changing then reverting omits that entry; unrelated assignments are preserved.
- [ ] Inject a later guard miss, stale witness and required history/Audit/Inbox/receipt failure on real native storage: every earlier assignment/effect rolls back or is gated to zero.
- [ ] Same actor/key/same canonical intent does not duplicate effects; different intent or command-family key reuse cannot bypass the original-operation owner.
- [ ] Finite aggregate cap is justified from actual binding/statement budget, validated at both boundaries and tested at/over the cap without partial chunking.
- [ ] Whole conflict makes old intent read-only and requires fresh baseline/reselection; known unchanged no-write stays editable; UNKNOWN never means success, failure or replacement submission.

## Implementation method

1. Before replacing the UI, add a purpose-specific person-scoped aggregate contract/command/result/reconcile beside current single-change APIs. Suggested command boundary: one targetUserId, explicit change entries carrying Department scope/action and exact expectedAssignmentId for withdrawal, one actor-owned operationKey and canonical request fingerprint. Reject empty/no-op, duplicate/contradictory scope entries, malformed/over-limit input before writes. Reordered equivalent sets must not cause duplicate effects; different intent with the same key is rejected.
2. Add only justified aggregate persistence beside the current immutable single-change receipt owner. Preserve original actor-wide key uniqueness across command families; an actor cannot reuse a key under a different endpoint to bypass intent protection. Represent parent receipt plus exact member outcomes if needed, retaining old receipt readers and history. Update server schema and generate a new migration using the next actual sequence; do not rewrite applied SQL or infer a batch result from unrelated individual receipts.
3. Reuse existing eligibility/current scope/witness guards at SQL time. Execute all assignments, per-change immutable history, Audit, required recipient Inbox and one aggregate receipt under a real native D1 all-or-none guard/assertion. A zero-row guarded UPDATE is a successful SQL statement: explicitly gate or abort the whole command so a guard miss/required-effect miss cannot commit the remaining changes. Prechecks alone, sequential HTTP posts and independently committed chunks do not satisfy this ticket.
4. Derive and document a finite change cap from actual bound-parameter/statement limits and mandatory effects. Validate it server-side and expose it as typed capability to the task; no magic 100-person assumption and no UI-only cap. Keep old single endpoints operational while callers migrate.
5. Use the #196 task frame/proof/lifetime. Fetch independently authorized current assignment state and withdrawal witnesses for visible scopes; unknown/loading/unavailable is never unchecked. Maintain an explicit net-change map from known baseline, omit reverted/untouched/unloaded entries and preserve unseen assignments. On whole-batch conflict show prior intent read-only, fetch a fresh authorized baseline, require new selection and explicit Save. On unchanged-baseline known no-write keep the choices editable. UNKNOWN reconciles only original actor/key under current authority.

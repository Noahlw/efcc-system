## What to build

An Admin or Role Assigner enters Manage, finds a permitted person and reads independently authorized responsibilities in the new prototype visual language. Search and detail work together on wide layouts; compact layouts use the same search through Change target. This slice is a complete authorized read journey, with existing working task destinations retained until their replacement slices land.

## Acceptance criteria

- [ ] Admin/RA can find and open only permitted targets; non-authorized and protected targets remain denied even via crafted requests.
- [ ] Search, selected detail and assignment paging remain bounded and independently authorized; unknown assignment status is not rendered unchecked.
- [ ] Wide layouts have no duplicate Change target; compact layouts reveal and focus the existing search; resize retains target.
- [ ] Phone stacks the same Department pair; desktop has two columns; arrows/dots/swipe/keyboard work and no visible fraction or initials remain.
- [ ] Loading, empty, invalid, unavailable and denied reads are distinct; 320px, 200% text, long Chinese names, keyboard/focus and reduced motion are exercised.
- [ ] Existing delivered command routes stay operable during incremental adoption; no new dead action or fixture actor selector is introduced.

## Implementation method

1. Prefactor only the current person-read/view boundaries needed by this journey. Keep authoritative readers feature-owned; compose their minimal identity, independent assignment/status and permitted-action results. Do not read a broad ManagedAccount or infer permissions from account badges. Admin/RA restrictions and crafted detail requests remain enforced server-side.
2. Add a shared person workspace that consumes bounded literal name/Username search (25 rows), validated query/page navigation and independently authorized selected detail. Assignment-group paging is independent of person-search paging. A known assigned record is not a complete unassigned baseline; expose loading/unavailable/unknown status where the source cannot yet establish it.
3. Keep RootFrame/PrimaryNavigation as the one shell. Use the production viewport <=1023px OR content container <=50rem compact conditions already agreed by #194; do not add device detection. When both panes are visible remove Change target entirely; in compact detail it reveals/focuses the same search. Preserve selected person across resize; guard late responses and dispose actor/target-owned protected data.
4. Extract the borderless Department duty-pair presentation: desktop one row/two columns; phone same pair/two stacked rows, nested Program hierarchy, native horizontal scroll snap, quiet labelled arrows/dots inside the component, keyboard/swipe access and accessible position. No visible 1/6 counter, auto rotation, dummy final group or name-initial avatar. Keep account identity and delegation visually grouped while task actions remain separate.
5. Establish one-row Back/title using the current header owner; long titles wrap inside their column. Use current tokens/controls and authorized navigation. Route old role-page entry points through the new browse owner as each is covered; preserve still-working command destinations during incremental delivery.

No framework/auth/session configuration migration or dependency upgrade. Query reads use actor/session/target/scope/filter/page keys as relevant and consume AbortSignal; cancellation is not authorization, write rollback or settlement. Keep one domain-owned original-operation lifetime. Sensitive mutations have no automatic replacement/remainder retry.
- Reuse `Button` variants primary/secondary/danger/quiet and theme tokens. Quiet for Back/add/roster-edit/search/candidate icon actions; primary for text task actions/Save/retry, secondary for Reset/cancel/navigation, danger only final own Admin exit. 17px body, >=44px targets, visible focus, concise Traditional Chinese/Cantonese. No generated name-initial avatars. Use existing Base UI focus/ref/disabled behavior; no handmade focus trap.
- `useAppForm`/field composition and Zod handle validation; explicitly parse command output where normalization/transforms are required rather than assuming validation changes onSubmit values. Hono/TypeScript types do not replace runtime validation or SQL-time authority. Do not duplicate form, command, permission or layout owners.
- Local unsent choices belong to the stable task; authorized remote state stays with the reader. Preserve valid same-task choices through conditional proof and known no-write, distinguish auth expiry, dispose protected state on actor/authority replacement and ignore late responses. UNKNOWN is neither success nor definite failure and never authorizes a replacement Save. No protected draft/password/person record storage in URLs or persistent browser storage.
- Scope discipline: use synthetic fixtures; do not import real member data. Any production API/DB work occurs only when a later implementation workflow is invoked. No merge/deploy, broad approved-spec overwrite, Department/Program CRUD, custom permission editor or S1/S2 redesign.

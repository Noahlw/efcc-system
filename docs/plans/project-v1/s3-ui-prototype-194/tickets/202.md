## What to build

An Admin grants Admin directly to an eligible Member/Staff from the account identity task, sees the target’s fresh-sign-in consequence and returns to fresh authorized person detail while remaining signed in as Admin.

## Acceptance criteria

- [ ] Eligible Member and Staff can each receive Admin directly; grantor remains Admin and signed in, target Sessions are revoked.
- [ ] Required native cleanup/history/Audit/Inbox/receipt effects and protected-target server guards remain valid.
- [ ] Confirmed grant returns to fresh allowed person overview with concise Session consequence; no acceptance or acknowledgement task exists.
- [ ] Expired proof/authentication, known no-write, lost response/UNKNOWN and actor replacement preserve the distinct established outcomes.

## Implementation method

1. Extend #196’s focused identity task with the separately confirmed Admin grant action/consequences, reusing existing Global role Admin grant command and receipt. Do not implement DB-only delegation, an invitation/ACK page, peer demotion, bootstrap or a new security owner.
2. Eligibility is current permitted Member/Staff, not a UI prerequisite to first become Staff. Reuse server current authority/eligibility guard and required cleanup/history/Audit/Inbox/receipt effects. Revoke every target Session as required while retaining grantor identity and Session. Show concise confirmed outcome and fresh authorized overview after success, not a success conclusion from a network response loss.
3. Reuse valid proof, conditional existing Security dialog, explicit Save and original-operation reconciliation. Render no final danger style for adding an Admin; danger is reserved for own exit. Protect other Admin/protected identities and stale target/actor responses under the authoritative matrix.

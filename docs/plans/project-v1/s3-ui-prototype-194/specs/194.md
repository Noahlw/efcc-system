## Problem Statement

Church administrators and delegated managers need to identify the right person or Program, understand the current responsibilities and finish a permitted change confidently on phone, tablet or desktop. Duplicate target-switch actions, inconsistent grouping and disconnected task controls make that work harder. The confirmed design should provide one coherent experience while preserving authority and honest outcomes.

S3 Roles and delegation has an existing Revision 2 implementation under [delivery parent #184](https://github.com/Noahlw/efcc-system/issues/184) / [PR #191](https://github.com/Noahlw/efcc-system/pull/191). Its current presentation is no longer the agreed visual target. The Owner completed the UI grilling/prototype refinement and explicitly requested this new UI specification and an update of [#29](https://github.com/Noahlw/efcc-system/issues/29) on **28 October 2026 (Hong Kong)**.

The new design must become maintainable production UI using the existing shared application structure and libraries. A standalone synthetic HTML prototype cannot simply be pasted into React or treated as proof of production authorization. Two accepted Save interactions also exceed the existing single-target/single-scope command contracts: one person's several scoped changes, and several people's grants in one Program. They need actual aggregate contracts rather than an atomic-looking frontend loop.

## Solution

**S3 UI contract Revision 1.** Give permitted users a clear person-first or Department-first route, understandable current duties, focused editors and dependable task actions across screen sizes. Adopt the pinned prototype's visual direction and the complete written behavior below. #29 Revision 3 remains the business/authority, mutation, history, Session and recovery authority; this issue owns the detailed S3 screen, interaction, responsive and frontend-integration contract. Neither replaces #184 as the delivery parent. Existing implementation and qualification remain tied to their original revision/source.

Deliver an **Operate** web/PWA interface: phone-first, readable Traditional Chinese/Cantonese, existing light teal tokens, concise controls and clear task ownership. Use existing production frames, navigation, controls, bounded readers, typed commands, security proof and recovery lifetimes. Redesign S3's old presentation; preserve applicable production behavior and shared foundations. Do not transplant the prototype's string rendering, fixture toolbar or synthetic transport into the application.

The Owner's request settles the UI design/grilling for specification publication; it does not certify every prototype state, the production implementation, security/atomicity, physical devices, independent review, merge or release. Technical contract work below is explicit, not a new unanswered product-policy frontier.

## User Stories

1. As an Admin, I want to enter person-first role management from Manage, so that I can maintain permitted accounts in one clear workflow.
2. As a Role Assigner, I want to find eligible Member targets through the shared person-first interface, so that I can maintain scoped duties within my delegation.
3. As a Department Manager without Staff identity, I want to enter my authorized Department and Program workspace, so that I can manage local Program leadership without church-wide account powers.
4. As a person holding several authorities, I want to see currently permitted work through Home, Inbox, Manage and Account, so that I can work without changing role identity.
5. As a person without role-management authority, I want to see only the delivered work I may enter, so that navigation does not suggest privileges I do not have.
6. As a role manager, I want to search by full name or Username through bounded results and paging, so that I can find the intended person without loading a directory.
7. As a role manager, I want to see full name and Username together, so that I can distinguish accounts with the same name.
8. As a role manager, I want to receive readable validation and empty-search feedback, so that I can correct a query without confusing an empty result with denial or failure.
9. As a role manager, I want to open independently authorized selected-person detail, so that I can manage a person safely even outside the currently visible result page.
10. As a two-pane user, I want to select another target directly from the visible search/list without a duplicate change-target button, so that switching people has one clear route.
11. As a single-pane user, I want to use Change target to reveal and focus the existing search, so that I can select a different person from the focused detail view.
12. As a tablet or desktop user, I want to keep the same selected account when the available width changes, so that resizing does not silently change whom I am managing.
13. As a role manager, I want to read current duties grouped by Department with nested Program responsibilities, so that I can understand the scope of each assignment.
14. As a phone user, I want to see each Department pair stacked in two rows, so that the same content remains readable in narrow space.
15. As a desktop user, I want to see the Department pair in one row and two columns, so that I can compare duties without changing the grouping model.
16. As a touch or keyboard user, I want to move between Department pairs using swipe or labelled arrows, so that every bounded group remains reachable without a mouse.
17. As a role manager, I want to see real single and odd final groups without dummy entries, so that the component reflects actual responsibilities.
18. As a role manager, I want to see quiet in-component position indicators and a clean nested hierarchy, so that navigation does not overpower the role content.
19. As a role manager, I want to open a focused scoped-duty editor for the selected person, so that the target and editable duties stay clear.
20. As a role manager, I want to see loading or unavailable status until each editable assignment baseline is known, so that unloaded data is never mistaken for an unchecked role.
21. As a role manager, I want to submit only explicit net changes while reverted, untouched and unloaded duties stay unchanged, so that one Save cannot replace responsibilities I did not review.
22. As a role manager, I want to save one person’s several permitted Department Manager and Program Leader changes atomically, so that the reviewed set either all applies or none applies.
23. As a Program manager, I want to edit an existing Leader through that Program’s limited context, so that a local action cannot spill into unrelated responsibilities.
24. As a Department Manager, I want to find permitted existing assignees for withdrawal after departure or restriction, so that cleanup does not depend on new-grant eligibility.
25. As a Program manager, I want to search only the eligible candidates permitted by current authority, so that the picker does not disclose an account or Department-member directory.
26. As a Program manager, I want to retain explicit candidate choices across bounded search and pages within the same Program task, so that I can assemble the intended selection without losing earlier choices.
27. As a Program manager, I want to toggle a candidate plus into minus and back before saving, so that I can select or cancel an unsent choice without changing a stored assignment.
28. As a Program manager, I want to view selected identities together and see the selected count, so that I can verify people chosen on different pages.
29. As a Program manager, I want to grant the selected people leadership in one Program as one all-or-none command, so that one invalid target or required-write failure cannot leave a partial selection applied.
30. As a Department Manager, I want to grant only to currently eligible Member candidates in the managed Department and Program, so that my local delegation respects its actual scope.
31. As an Admin, I want to manage Global account identity separately from Membership status and scoped duties, so that an identity change does not silently alter church relationships.
32. As an Admin, I want to submit Role Assigner delegation independently for eligible Staff, so that a visual grouping does not combine separate account and delegation commands.
33. As a phone user, I want to see current identity and delegation under one Account identity and delegation heading, so that I understand their relationship while keeping their separate actions.
34. As an Admin, I want to grant Admin directly to an eligible Member or Staff and remain Admin, so that adding an administrator is separate from leaving my own role.
35. As an Admin granting another Admin, I want to see the target’s fresh-sign-in consequence and a concise authoritative outcome, so that I understand the Session effect without an unnecessary acknowledgement page.
36. As an Admin leaving my own role, I want to choose Member by default or Staff explicitly from my own Account task, so that the resulting identity is deliberate.
37. As an Admin considering self-step-down, I want to be prevented from leaving without another effective Admin, so that the church retains effective administration.
38. As an Admin whose self-step-down response was lost, I want to receive honest uncertainty and normal eligible navigation after sign-in, so that the interface does not invent a receipt exception or certainty.
39. As a user editing a task, I want to keep applicable Save and Reset controls at the bottom of the available viewport, so that I can find the next action without covering fields or errors.
40. As a user editing a task, I want to reset unsent choices to the known baseline, so that I can undo my draft without cancelling a submitted command.
41. As a phone user, I want to keep shared navigation while browsing and focus on edit/review tasks with it temporarily hidden, so that navigation supports the current task and returns afterward.
42. As a user with a long task title, I want to keep Back and title in one header row with readable wrapping, so that the return path remains predictable.
43. As a keyboard or low-vision user, I want to have readable body text, adequate action targets, contrast and visible focus, so that I can operate the same tasks reliably.
44. As a Cantonese reader, I want to receive concise Traditional Chinese labels and actionable feedback, so that I can understand the task without API or receipt jargon.
45. As a role manager, I want to identify people through meaningful full name, Username and role text without generated initials, so that the interface remains clear without decorative identity badges.
46. As a user with valid current password confirmation, I want to save without another role-password prompt, so that existing valid proof is reused.
47. As a user whose confirmation has expired, I want to confirm through the existing Security flow, return with authorized unsent choices and explicitly Save, so that confirmation does not lose choices or submit automatically.
48. As a user whose authentication has expired, I want to receive the existing authentication recovery instead of being treated as merely missing confirmation, so that the interface respects the actual Session boundary.
49. As a user with unsent changes, I want to choose Keep editing or Discard on an app-controlled departure, so that I decide whether to retain the draft before leaving.
50. As a role manager, I want to see loading, empty, denied and unavailable outcomes distinctly, so that a failed or forbidden read is not presented as an empty successful result.
51. As a user correcting an invalid submission, I want to see linked field or form errors while valid same-task choices remain, so that I can correct the problem without starting over.
52. As a user after a known no-write rejection, I want to retain valid editable choices and usable search or paging on the unchanged baseline, so that I can deliberately retry the intended work.
53. As a user after a whole-batch conflict, I want to see the old intent only as a read-only reference, refresh current data and choose again, so that a stale selection is not automatically merged or resubmitted.
54. As a user with an UNKNOWN result, I want to resolve only the original operation under current authority, so that a lost response cannot create a replacement or duplicate effect.
55. As a person switching accounts or losing authority, I want to have protected old labels, drafts and late responses discarded, so that the next account cannot inspect or replay previous work.
56. As an account holder, I want to read permitted minimal historical role events in the existing Inbox, so that I can learn about changes without receiving management receipts or another person’s data.
57. As an account holder, I want to see Home content according to current independent access, so that withdrawn duties do not persist through stale presentation and valid other access remains.
58. As a role manager after a confirmed save, I want to return to the appropriate fresh person overview or Program roster, so that the outcome and next work stay in context.
59. As a user preferring reduced motion, I want to receive selection feedback without unnecessary animation, so that the toggle remains understandable and comfortable.
60. As a phone user using large text or the software keyboard, I want to keep final fields, errors, focus and task actions reachable, so that the shared footer does not obstruct completing the task.

## Implementation Decisions

### UI01 — Authority, scope and vocabulary

- Apply #29 Revision 3's full actor/target/scope, eligibility, confirmation, effective-Admin, Session, history, Audit, Inbox, deletion and UNKNOWN rules. A visible control or URL is never authority.
- Keep Global account identity **Member / Staff / Admin** separate from Membership status. **Role Assigner** is delegation for Staff, not another exclusive account identity. Department Manager and Program Leader are additive scoped duties, not Department membership or Program enrolment. Preserve independently valid responsibilities.
- Cantonese UI mapping: 人員權責 for the person overview; 部門主管 for Department Manager; 聚會負責人 for Program Leader; 職務指派權 for Role Assigner delegation. Program remains the existing domain Program, not a new Activity entity. Use full name plus Username to distinguish people. No new domain term or ADR is needed for this presentation refinement.
- Department/Program screens here maintain **roles**, not Department membership, Program enrolment, CRUD, archive/movement, Event, attendance or notice-authoring workflows. Those retain their own feature owners.

### UI02 — Shared shell, entry and navigation

- Preserve Home / Inbox / Manage / Account and the current production shared shell/PrimaryNavigation ownership. Show only currently authorized delivered work; ordinary Staff/Program Leader alone gain no role-management entry. Existing independently authorized Staff tools remain reachable through their existing entry.
- Admin/Role Assigner use bounded person-first management. Department Managers use Department → Program → current Leaders; Department membership of the acting manager is not a new prerequisite. Do not introduce a role-identity switcher, a configurable permissions editor, a generic recovery dashboard or Own Responsibilities page.
- Phone browse/search/overview/workspace keeps shared navigation. Focused edit/review tasks temporarily hide phone navigation and restore it on return. Desktop retains the shared sidebar. Keep a clear Back/title header on one row; long titles wrap within their own column, not by pushing Back onto another row. Do not add redundant breadcrumb chrome.
- Use one current production page scroll owner. Views must restore the authorized calling context (person overview or Program roster, applicable search/page/selection) rather than land on an unrelated generic page.

### UI04 — Adaptive person search and target switching

- When search/list and detail are simultaneously visible, **hide the redundant「更換對象」button**. The identity card contains target identity; use the existing search/list directly to select another account.
- In the existing single-pane composition, retain the secondary「更換對象」button. It reveals and focuses the same search. This applies to phones, constrained tablets and zoomed/narrow desktop windows alike.
- Reuse both current layout conditions: viewport-owned compact composition and available-content container composition. Do not add a device-name test, a separate breakpoint, another target-picker state owner or an empty placeholder for the hidden button. Preserve the selected account through resize; invisible controls must not remain keyboard/accessibility-tree actions.
- Keep protected selection/draft disposal and late-response handling with their existing lifetime owners. Directory search state is not submission intent for a newly selected person.

### UI05 — Department duty component and hierarchy

- Share one Department-pair model and semantic component: **desktop one row/two columns; phone the same pair stacked in two rows**. Further pairs scroll/swipe horizontally with native overflow/snap and keyboard support.
- Keep the component clean without an enclosing outline. Department headings, indented role/Program content, the subtle existing hierarchy guide and spacing distinguish Department → Program; no nested decorative card collection.
- Quiet previous/next arrows and small nonnumeric position dots belong **inside the same duties component** as its content. Hide visible numeric fractions/counts on both layouts; keep accessible position announcements and real disabled edges. No automatic rotation. An odd final pair contains only the remaining Department; a single available page has no unnecessary navigation or dummy entry.
- Preserve logical pair position during resizing, bounded assignment paging separately, and person/page-scoped position ownership. Clear it on person/page/actor replacement. Do not load the whole assignment catalog merely to implement a carousel.

### UI06 — Account identity and delegation grouping

- Phone and desktop use one「帳戶身份與委派」semantic section. Phone shows current identity and Role Assigner delegation as subordinate label/value rows, with matching hierarchy rather than two peer sections separated by a divider.
- Keep their existing separate management buttons and independent task/save ownership. Visual grouping does not imply atomic identity+delegation changes. Admin-target/own-exit rules remain unchanged.

### UI07 — Shared controls, sizing and visual language

- Use the implemented theme tokens, type scale and Button CVA variants; no replacement palette or framework. Preserve 17px body baseline, at least44px actionable targets, readable supporting labels, AA contrast, visible focus and responsive long-name/Username wrapping. Adapt geometry to control purpose rather than making every control a large filled block.
- Quiet icon-only Back, entry/add, roster edit, search and candidate selection use semantic library icons, accessible names and visible hover/focus/pressed states. Primary text buttons remain for Edit/Manage/Save/progress/retry actions. Cancel, Reset, compact target-switch and bounded paging retain their appropriate secondary recipe. Reserve danger for final own Admin exit, not ordinary withdrawal or an unsaved minus toggle.
- Remove generated name-initial/monogram avatars entirely. Retain meaningful full name, Username and existing role/status badges; do not replace initials with empty circles, em-dashes or decorative generic-person icons. Unicode identity/sign-in/storage semantics remain unchanged. Whole-repo work stays with [#193](https://github.com/Noahlw/efcc-system/issues/193).
- Use concise Traditional Chinese/Cantonese product copy. Avoid exposing API/receipt/transport jargon as user instructions. Distinguish「將新增／將撤回」from committed success and uncertainty from definite failure. No ordinary duplicated「變更摘要」block or new review page merely to repeat the editor's person/action/role/scope.

### UI08 — Shared viewport-bottom task actions

- Applicable S3 editors and multi-selection tasks share a shell-owned action slot at the bottom of the available viewport, outside the **one** page scroll owner. The footer takes real layout space: last fields, errors, focus and controls remain reachable and unobscured.
- Show count/context and Reset/Save for real unsent net choices; clean/reverted ordinary settings have no dirty footer. Submitted pending/UNKNOWN is a separate operation state, not a new editable draft. Final Admin-exit confirmation follows its own explicit command semantics, not an inferred ordinary dirty-only rule.
- Reset restores the task baseline and clears unsent selection; it does not cancel a submitted command. Pending prevents duplicate mutable actions. Adapt wrapping, safe areas, changing footer height, large text and software-keyboard/visual-viewport changes without adding another scroller or a detached overlapping fixed bar per screen.
- Extend/extract the minimal shared production frame/control seam, with feature-specific task owners supplying content/actions. Do not copy the entire shell/form for each role or introduce a universal component with a large boolean-prop matrix. Broader migration of existing Account-data save surfaces remains [#192](https://github.com/Noahlw/efcc-system/issues/192), not an S1/S2 redesign here.

### UI09 — Q30: one person, multiple explicit scoped changes

- Department-grouped DM/PL choices produce one **bounded explicit net-change set for the selected person** and one Save. Identity/Admin and Role Assigner are not part of that batch. A Program-specific editor still limits its scope.
- Only independently authorized, successfully read assignment baselines can be edited. A catalog row or absence from a partial page is not an unassigned baseline: show loading/unavailable and withhold mutation until the relevant current status/witness is known.
- Preserve untouched and unloaded assignments; changing a choice back to baseline removes it from the request. Review target, action, fixed role and scope through the editor's content/markers before explicit Save.
- One aggregate command, original operation key/fingerprint and settlement result commits every required effect/history/Audit/Inbox/receipt or none. Carry each touched withdrawal's exact reviewed assignment witness and all current mutation-time guards. No frontend loop over single-change endpoints. #29 D03b/D07 define the mutation contract; endpoint/type names and concrete finite limits are implementation contract work, not invented routes here.

### UI10 — Q35: several people, one Program, grants only

- The Program header plus opens the candidate picker. Candidate-row plus is a **toggle**, not an immediate grant; selecting animates plus to minus, with stable accessible label/aria-pressed and reduced-motion support. Minus cancels an unsaved choice, not an existing assignment. Existing-grant withdrawal stays in its scoped editor.
- Preserve explicit selected IDs and minimal already-authorized identities across bounded search/pages in the same Program/task, with selected-only viewing and count in the shared footer. No select-all-results, full directory, cross-Program target batch or bulk withdrawal.
- All selected grants succeed or none writes. Apply every actor/target/current Program/eligibility condition at the actual write boundary, including DM candidate Department membership and the distinct Admin/RA rules. Reuse #29 D03a's one operation/fingerprint/protected result, required-write atomicity and lifetime.
- Select a finite request bound against transport/native D1 limits before implementation; reject oversize before effects. Never display an unbounded selection promise or implement atomic-looking Save by serial posts.

### UI11 — Confirmation, unsent edits and task lifetime

- Reuse valid current Session/credential-bound ten-minute confirmation. No permanent extra role-password field or second confirmation protocol. Password-confirmation expiry is distinct from auth-Session expiry: invalid authentication follows existing auth recovery, not a fictitious successful role task.
- If proof is missing/expired, use the existing Security-owned form/protocol, retain choices only in the same still-authorized unsent task, return there, and require a **new explicit Save**. Do not auto-submit, transfer proof to a new account, or rebind an already submitted original operation.
- App-controlled departure from real unsent net changes offers Keep editing/Discard; clean/reverted values leave normally. Conflict's exceptional read-only previous reference is not an unsent draft. Submitted UNKNOWN uses its original recovery rules rather than the discard dialog.
- Clear protected names/scopes/results/unsent choices on logout/actor or authority replacement and ignore late responses. Surviving submitted recovery metadata remains only the permitted minimal original actor/opaque key; no password, protected draft or copied directory in URLs/storage.

### UI12 — State and feedback contract

| State | Required behavior |
| --- | --- |
| Loading/current status unknown | Truthful pending presentation; do not treat unloaded/partial absence as unchecked or enable guessed writes. |
| Empty | Purpose-specific authorized empty state, with search/navigation where applicable; never disguise denied/unavailable as empty success. |
| Validation | Labelled inline error, focus/recovery path, valid same-task choices retained; no write. |
| Known no-write/service rejection | Explain no save; retain valid editable choices on the unchanged baseline and restore usable search/paging. |
| Denied | Safe current-authority feedback; remove protected stale presentation/actions. Do not leak protected target/contact/history detail. |
| Conflict, whole batch definitely no-write | Preserve original intent only as a read-only exception reference; read latest authorized baseline, require fresh selection and explicit Save. No automatic merge, rebinding, partial retry or resubmission. |
| UNKNOWN | Neither success nor definite failure. Resolve/retry only the original actor-bound operation under current applicable authority; no replacement Save or inferred settlement from denial/missing receipt/Inbox. |
| Confirmed | Present only the authoritative committed outcome and return to the appropriate fresh authorized overview/roster. Do not duplicate effects or add unnecessary acknowledgement pages. |

Self-step-down retains its strict post-revocation boundary: no special receipt reader or certainty from a new sign-in/personal notice. Keep this distinct from ordinary protected reconciliation.

### UI14 — Documentation-checked implementation method

Checked with Context7 plus official upstream documentation on28 October2026. Installed manifest pins are React19.3.0, TanStack Query5.104.1, Form1.33.5, Base UI1.8.0, CVA0.7.1, Hono4.13.12, Zod4.6.5 and Drizzle0.45.3. This is not a dependency upgrade. Context7 supplied v5/v1/current docs rather than exact Query5.104.1/Form1.33.5 snapshots; current Base UI/Hono docs can also be newer than installed pins. Use supported existing wrappers and verify any new API against the pinned declarations/source during implementation. No exact-version runtime/typecheck is claimed by reading docs.

| Seam | Planned method and important limit |
| --- | --- |
| React task identity | Keep one stable task/form owner through an in-task proof dialog. Reset/dispose only at the real actor/target/setting/scope boundary or explicit Reset/Discard; never key the form by search text, responsive layout or proof freshness. React state follows component identity/position and keys can intentionally reset it. [React state identity](https://react.dev/learn/preserving-and-resetting-state). |
| Authorized remote reads | Where the existing reader uses TanStack Query, keys include every changing reader dependency, including actor/session lifetime, target, scope and bounded query/page. Consume queryFn AbortSignal to cancel obsolete reads; cancellation is an optimization, not authorization, mutation rollback or settlement. Keep existing lifetime/late-response guards and actor-owned cache disposal. Avoid carrying prior-person protected data as placeholder data for the next target. [Context7 Query keys](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/query-keys.md), [cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation). |
| Forms and Zod | Reuse the existing useAppForm/field owner and Zod Standard Schema integration for typed values/validation. Form validation does not substitute transformed schema output into onSubmit: explicitly parse where the command contract requires output normalization/transformation; validate independently at the server boundary. Map errors through the current field/form presentation and retain valid same-task unsent values across proof/no-write. Do not reset a mounted form merely because confirmation returns or a reader refetches. [Context7 Form validation](https://tanstack.com/form/latest/docs/framework/react/guides/validation), [submission handling](https://tanstack.com/form/latest/docs/framework/react/guides/submission-handling). |
| Submission and retry | Keep role-command-lifetime as original-operation owner; do not introduce a competing mutation/recovery controller simply to use another hook. If TanStack useMutation is used for transport, preserve the same operation key/fingerprint and explicitly disable automatic sensitive mutation retries; permission/proof/UNKNOWN handling stays domain-owned. A network abort cannot cancel an already committed command. [Mutation retries](https://tanstack.com/query/latest/docs/framework/react/guides/mutations). |
| Controls and dialogs | Production Button already implements primary/secondary/danger/**quiet** through CVA and Base UI; use that typed variant rather than inventing ghost or a parallel CSS button. Preserve native/Base UI disabled/ref/keyboard behavior and Lucide geometry. Use existing dialog composition for controlled proof/unsent/recovery presentation, with labelled title/description and initial/return focus; verify any new focus prop on Base UI1.8.0 rather than copying a newer example. No manual focus trap or prototype showModal/string-DOM transplant. [CVA variants](https://cva.style/getting-started/variants/), [Base UI Dialog](https://base-ui.com/react/components/dialog). |
| Typed HTTP contract | Extend feature-owned strict schemas, typed routes/results and existing Hono client inference where used. Keep server/runtime validation and SQL-time authority; TypeScript types are not a security boundary. Hono RPC infers handler inputs/outputs with strict typing, not authorization. Avoid a second route/schema/permission owner. [Hono RPC](https://hono.dev/docs/guides/rpc). |
| Native D1 aggregate write | Reuse the current native prepared-statement/write owner; D1 batch executes a sequence transactionally and rolls back on a SQL failure. This does **not** mean a successful conditional UPDATE that changed0 rows aborts the transaction. Every required guard/effect must participate in an aggregate all-or-none SQL guard/assertion path, with injected guard-miss and required-write failure tests proving no partial assignments/history/Audit/Inbox/receipt. Do not rely on outside-transaction prechecks, sequential HTTP posts, or an assumed generic ORM/interactive transaction wrapper. [Context7 D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [SQLite UPDATE](https://sqlite.org/lang_update.html), [D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/). |
| Finite request budget | Derive the target/change cap from the actual parameter and statement budget, including actor/scope/witness/required-effect overhead, not an arbitrary UI selection count. Context7's current D1 limits list100 bound parameters **per query**, not100 people per operation. Record and validate the resulting finite command limit before effects; do not chunk one promised atomic Save into independently committed batches. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/). |

These are planned methods verified against docs and current ownership, not new implemented guarantees. Drizzle/auth/session configuration, framework migration and library upgrades are unchanged; new aggregate D1 correctness still needs real native qualification. Private raw Context7 results are retained with this publication's source audit.

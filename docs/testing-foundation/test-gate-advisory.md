## Terms for this discussion

These are engineering-workflow labels, not additions to EFCC's business-domain glossary:

- **Commit checks:** checks required to save the exact staged source. Passing does not establish delivery readiness.
- **Development feedback:** explicit affected checks and risk-specific runtime scenarios during implementation. A diagnostic subset is not complete qualification.
- **Candidate qualification:** applicable required verification for an identified source tree and base, including selection/execution completeness and cleanup. It is not merely the exit status of one test command.
- **Progress:** informational stage, elapsed-time and completion observations. A heartbeat shows the progress owner is alive, not that a child is making useful progress.
- **Measurement versus gate:** a measurement supplies information; a gate makes an explicit acceptance decision. Integrity checks around a report do not make its numeric score a quality threshold.

## External comparison

### First-party guidance

1. [Software Engineering at Google, chapter 23](https://abseil.io/resources/swe-book/html/ch23.html): CI asks which tests run when, balancing fidelity/setup cost. Fast reliable presubmit is recommended; exhaustive presubmit disrupts engineers. Its postsubmit/rollback model is not automatic permission to move EFCC security/atomicity qualification past merge.
2. [Google test sizes](https://testing.googleblog.com/2010/12/test-sizes.html) and [testing overview](https://abseil.io/resources/swe-book/html/ch11.html): resource constraints distinguish small/medium/large tests. Framework labels alone do not establish speed. Published example time limits and test mix are not universal targets.
3. [Vitest 5.0.3 CLI](https://github.com/vitest-dev/vitest/blob/v5.0.3/docs/guide/cli.md), retrieved using Context7's version-specific library ID: `related --run` is intended for hook/CI feedback but uses static import reachability, not computed dynamic imports. It cannot replace EFCC's semantic Native policy. A safe fast phase must account for non-import/config/subprocess consumers, changed tests and unknown paths.
4. [Vitest performance guidance](https://vitest.dev/guide/improving-performance): profile first. Phase totals overlap across workers and are not wall-clock percentages. More workers, disabled isolation or a pool change are tradeoffs, not guaranteed acceleration. Do not run multi-pass `doctor` casually as a cheap probe: it executes the suite repeatedly.
5. [Playwright best practices](https://playwright.dev/docs/best-practices): test user-visible behavior, isolate mutable test state, use native locators/assertions, measure parallelism and avoid always-on expensive tracing. EFCC already has isolated native fixtures, two default feature workers and retain-on-failure traces. Generic CI retry/shared-auth examples do not replace EFCC first-attempt and actor-isolation requirements.
6. [Playwright reporter API](https://playwright.dev/docs/api/class-reporter): structured lifecycle events support progress. Reporter exceptions are not a reliable acceptance mechanism; final results/receipts must remain authoritative.
7. [Stryker configuration](https://stryker-mutator.io/docs/stryker-js/configuration/): `break` controls score-based failure; high/low display bands do not. This matches the repository's explicitly informational pilot, not a quality score gate.
8. [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks): required checks bind to current SHA/test merge status. Some skipped/neutral statuses count as successful; a green badge alone cannot prove complete execution. Strict up-to-date and merge-queue enforcement are separate configurations. A local receipt is not a server-enforced check.
9. [lint-staged official TypeScript guidance](https://github.com/lint-staged/lint-staged#how-can-i-resolve-typescript-tsc-ignoring-tsconfigjson-when-lint-staged-runs-via-husky-hooks), retrieved through Context7: project typechecking is supported, but staged filenames must not be appended to `tsc` or its tsconfig semantics change. EFCC already invokes the complete `typecheck` script separately from filename-based formatting; retain that separation and snapshot authority rather than introducing an extra typecheck owner.
10. [GitLab's testing levels](https://docs.gitlab.com/development/testing_guide/testing_levels/): isolated units, component behavior, request-level integration and full-system journeys answer different questions. Its test distribution, Ruby/Vue-specific mocking rules and pipeline deployment choices are not EFCC requirements. Google separately distinguishes test scope from resource size, so a Vitest test that spawns processes is not a small test merely because its filename ends in `.test.ts`.
11. [Playwright running tests](https://playwright.dev/docs/running-tests): selected files/projects and complete suites are supported natively. Targeted development execution is legitimate, but a diagnostic subset does not establish complete candidate qualification.

No cited official documentation mandates an identical pre-commit/CI/Ready matrix for all repositories or requires replaying the base branch's entire suite to collect candidate coverage. The recommended phase ownership is an EFCC engineering decision informed by those documented capabilities and feedback principles, not an invented external standard.

## Recommended direction for confirmation

1. **Keep one runner and existing owners.** Preserve source-impact policy, immutable staged/source exports, native lint-staged partial-hunk handling, privacy, drift checks and existing evidence owners. Do not add another workflow driver, scheduler or pass cache.
2. **Every commit keeps static checks.** Run staged formatting/lint, complete project `check` including runtime boundaries, and complete project `typecheck` including `wrangler types`. Then run affected genuinely fast contracts without coverage. Related-test reachability is only an optimization: configuration, computed imports and subprocess consumers require a conservative fast-suite fallback. Unknown source classification still fails closed; zero related matches alone never establishes safety.
3. **Separate retained cost classes.** Pure product contracts, SSR and small tooling contracts form the fast class. Gate bootstrap, full Native collection and process/lifecycle/timeout integration probes remain retained but are not ordinary commit work. Classify behavior, not framework/directory; do not shorten safety deadlines or exclude all tooling. Full Node execution continues to include every retained class.
4. **Development remains risk-driven.** Use the existing affected/source-bound path for relevant HTTP/D1/Native/browser/mobile/causal/dev feedback early when those boundaries change. Targeted diagnosis is not qualification. Keep semantic selection and required engines; import-only selection does not replace them.
5. **Preserve automatic CI scope in this PR.** Keep actionlint, event/source validation, check/typecheck and one candidate coverage run of the complete existing Node suite, including tooling integration tests. Add safe progress/timing. The hard advisory considered fast-only CI, but the coordinator rejects that here: it would reduce automatically checked runner regressions while CI is not the ordinary local commit bottleneck. Later CI scheduling optimization must preserve those cases and required-check meaning.
6. **Qualification remains complete and source/base-bound.** Before Ready/pre-merge, execute all applicable required Node/coverage/build/Native/mobile/causal/dev and governed presentation obligations, plus the existing scoped mutation pilot. Explicit full/toolchain/spec-required full scopes retain the complete agreed matrix. Missing, failed, partial, stale-source/base or unverified-cleanup evidence cannot satisfy local readiness. Avoid redundant full gate aliases and ordinary-unit-plus-coverage duplication.
7. **Retain the applicable advisory base comparison at qualification, after required Native feedback.** Remove it from ordinary commit execution, not from its approved delivery responsibility. Candidate coverage remains mandatory with complete source inventory and unchanged assertions. Base incompatibility/failure stays advisory/incomparable, no fabricated delta; cleanup failure still blocks. The hard advisory recommended opt-in, but the coordinator does not adopt that policy change in this first PR: issue #182 and current testing docs require the applicable comparison, and no controlled measurement establishes that its review value is insufficient. Opt-in would require a separate explicit Owner-approved amendment, not a claim that official docs authorize removing a project obligation.
8. **Keep mutation applicability unchanged.** Move the bounded pilot out of commits, retaining its source/direct-test/config/toolchain/full-policy applicability at qualification. Do not add a score threshold, cancel it or claim broader mutation coverage.
9. **Use #206 for observability.** Structured safe stage/project elapsed wall time, monotonic completed/failure counters and bounded heartbeat; actual selected Native matrix supplies denominators. No public test names/IDs/paths, raw-log scraping, fake ETA, telemetry service or acceptance from progress. Detailed per-test timing stays private. Measure export/install/format, units, builds, discovery, Native lanes, advisory work and cleanup separately; parallel durations are not wall-clock totals.
10. **Optimize repeated work only with proof.** Investigate double bootstrap and repeated collection within tooling tests. Do not borrow mutable dependencies, raise workers blindly, relax isolation, shorten genuine timeout probes or combine production/native output writers. Only existing validated immutable compiled artifacts may be reused; passing results and mutable resources never are.
11. **Disclose enforcement limits.** GitHub light CI remains automatic. Local readiness rejects invalid evidence but does not prohibit direct GitHub UI Ready/merge actions; accepted author/reviewer delivery responsibility remains. No ruleset change, signing service or hosted Native pipeline is included.

Official docs provide capabilities and engineering recommendations, not a universal mandatory gate matrix. Google supports fast reliable early feedback; Vitest supports targeted development and complete validation; lint-staged documents project typecheck without staged filename arguments; Playwright supports targeted/full execution. EFCC's approved source/privacy/risk requirements determine exact final obligations. No test-claim deletion, lower coverage requirement, assertion weakening, mutation expansion or automatic base-comparison cancellation is proposed.

## Proposed acceptance measurements, not speed promises

Measure comparable synthetic candidates on the same host and pinned toolchain, separating warm store/native artifact hit from cold install/build. Report ordinary commit wall time, time to first useful failure, full qualification wall time and per-stage breakdown independently. Exercise a passing commit, a fast-check failure, preserved partial staging, index drift, required qualification failure/missing/incomplete receipt, changed source/base invalidation, non-TTY live progress, reporter corruption and interruption/cleanup. The test-gate change itself still requires the trusted-base obligations or an explicitly approved amendment; it cannot waive its own review/qualification.

The first PR should not become a test-framework rewrite. A deeper suite-claim reduction, different browser matrix, score threshold, hosted Native pipeline, new receipt signing service or a performance SLA requires a separate explicit decision supported by measurements.

## Deepening candidates

1. **Shared presentation frame module — Strong.** Concentrate viewport sizing, gutters, header/title alignment, root nav reservation and focused-work scroll rules behind a small seam. Actual root/task/auth families justify the variation. Deletion test: removing it would scatter the same geometry rules back through routes. Locality: fix a frame rule once. Leverage: exercise all route families through the same presentation interface while server routes retain access/data ownership.
2. **Tokens and bounded variants module — Worth exploring.** Extend existing controls/tokens for real delivered roles. Assess stable CVA only where the variant matrix earns its dependency; no broad theme/plugin framework or catch-all style options. Deletion test: a pass-through class helper can be removed; a shared intent/size matrix earns its keep when it replaces repeated branches. Test surface: the actual rendered controls and production build, not tests copying class strings.
3. **Auth and outcome presentation module — Strong for the named drift.** Give Sign-in, authentication-required, sign-out pending/unknown and related outcomes common compact geometry, readable copy and action grouping. Preserve each feature's action owner. Unavailable, denied, unknown and confirmed remain distinct. Locality: visual sizing rules concentrate; leverage: multiple real outcomes use one family. A generic recovery controller or fake success adapter would violate the existing contracts.

4. **Staff person-first work module — Strong for accepted Q5; presentation extraction requires judgement.** Concentrate search, selected-person context and work navigation across the existing four callers. Target/operation decisions and per-action eligibility remain in the current feature modules. Extracting only an option string would be shallow; the full consistent context earns depth and a real test surface.
5. **Feature form/review organisation — Worth exploring throughout all eight modules.** Reuse current field descriptors and review sections, then concentrate genuinely repeated fields, summaries, outcome/actions and dialog presentation. Preserve existing TanStack/native adapters and original state ownership. An extraction that merely moves complexity without improving locality should not be introduced.

The priority is the whole UI foundation: shared frame/token/control rules across all families, shared truthful outcomes, Staff person-first work, and bounded form/review organisation wherever the census demonstrates friction. Auth is one case within this scope. Exact interfaces and CVA adoption remain tied to actual repeated roles. No glossary term is added for implementation vocabulary; no ADR is warranted for a reversible styling utility. Revisit ADR necessity only if an accepted architecture trade-off actually makes later reversal costly.

## Route Groups, shared nested layouts and roles — assessment

The owner supplied the ChatGPT discussion “學習 Next.js基礎” and asked whether its Authenticated Route Group with Shared Nested Layout recommendation remains valid with EFCC roles. This is an assessment, not a route migration or replacement role specification.

**Recommendation:** use shared presentation frames; URL-transparent Route Groups and a thin shared nested layout are suitable organizational tools where they remove delivered duplication. Do not partition the application into a separate route tree per role or make a persisted layout the authorization boundary. Root, task and Auth presentation roles remain distinct, including root-only mobile bottom navigation.

Verified current source: `src/proxy.ts` validates native session and current membership/security state, strips caller-supplied identity headers and injects its decision. `src/app/primary-navigation.tsx` renders permitted destinations from current server inputs. `src/features/account/decisions.ts:requireStaff` checks current session, credential revision, membership, ban and Staff/Admin authority against D1 close to data/actions. These checks must survive frame extraction. Repeated database reads may be optimized only after proving the same freshness and request boundary; “never check session again” is not a safe refactoring rule.

Legacy reference: the locally available EFCC source snapshot `apps/web/lib/identity/role-hierarchy.ts` projects action affordances from capabilities and recomputes D1 authority on calls; its own comment says the UI projection is never authority. That snapshot is a design reference, not verified-current legacy runtime or rebuild policy. Current [Slice 3 spec #29](https://github.com/Noahlw/efcc-system/issues/29) instead specifies an exclusive Member/Staff/Admin global role with additive Department Manager/Program Leader responsibilities and Staff-only Role Assigner delegation. A person can hold several independent scopes. It explicitly rejects a custom-role editor/configurable permission engine. Removing one assignment must preserve independent authority.

Official Context7 `/cloudflare/vinext` and [vinext routing documentation](https://github.com/cloudflare/vinext#routing) confirm URL-transparent Route Groups and nested layouts. Its [layout example](https://github.com/cloudflare/vinext/blob/main/examples/app-router-playground/app/layouts/readme.mdx) explains state preservation/reuse on navigation. [Next.js auth guidance](https://nextjs.org/docs/app/guides/authentication#layouts-and-auth-checks) warns that layouts do not rerender on navigation and recommends checks close to data; hiding children is not a security boundary. Documentation support is not tested compatibility of a future EFCC migration.

Implementation qualification must exercise direct URL/API access, restricted and temporary-password gates, revoked role/scope on subsequent requests, account switching, navigation freshness, BFCache private-page revalidation, unchanged URLs/proxy matchers, error boundaries and root/task navigation. Keep protected reads/actions authoritative. Do not mount the whole application as a client component or add a generic permission framework for shared styling.

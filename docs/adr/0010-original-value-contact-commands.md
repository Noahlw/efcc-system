# Original-value contact commands

The Owner approved [original-value comparison and explicit refresh](https://github.com/Noahlw/efcc-system/issues/106#issuecomment-6263423285), [legacy receipt compatibility](https://github.com/Noahlw/efcc-system/issues/106#issuecomment-6263466754) and [versioned operation binding](https://github.com/Noahlw/efcc-system/issues/106#issuecomment-6263519654). This applies to Own Phone, Staff Identity correction and Applicant correction. The current R1–R5 implementation authorization is recorded in #106; historical planning-only footers do not grant release approval.

The submitted baseline contains raw stored values, including null, display/canonical Username and the 0/1 sharing flag. Own Phone compares phone and sharing; the two full contact commands compare canonical/display Username, full name, email, phone and sharing. These are write dependencies, not authorization. Current Session, credential, role, Ban, target, confirmation, verification, application/history and projection checks remain at their existing owners. Comparison is repeated inside the same atomic D1 batch as all domain, Search, Application, Audit and Receipt changes. A mismatch returns `409 stale_identity` without partial effects. Value comparison deliberately permits A→B→A when every relevant value matches again; there is no Identity Revision column.

Identity retains its existing HMAC over actor/action/input; v2 wraps parsed input as `{ input, protocol: "identity-contact-v2" }`. Applicant correction retains SHA-256 and uses the ordered tuple `["applicant-contact-v2", actorUserId, parsedInput]`. Each includes the original and proposed values, original operation key, action and target/application. Existing contract declaration order and normalization are deterministic. Changed original or proposed values under a completed key are a conflict. Unrelated actions retain their existing recipes.

A missing original-value precondition is permitted only for matching completed-receipt recovery using the exact legacy fingerprint. A fresh legacy command returns `409 client_update_required`; it cannot fall back to an unguarded write. Legacy receipts and hashes are immutable, and receipt recovery does not compare historical originals with today's mutable data or execute the old mutation. All receipt disclosure still requires current operation-specific authority. There is no pending-intent store or new operation table.

TanStack Form owns the draft/review; existing transient TanStack Query ownership handles an explicit authorised refresh. Changed source or a stale response displays the approved refresh warning and blocks submission. The draft and baseline remain until the user confirms discard and a successful authorised read returns the intended actor/target's latest values. Cancel, network failure or malformed data does not replace the draft with blanks. Current authority loss disposes the private task. Verified recovery-method availability may become unavailable without rebasing the editable contact values; the user must select and acknowledge a currently permitted method again.

Submitted requests are frozen in memory. Persistent storage retains only the existing non-secret operation metadata. UNKNOWN, denied reads and momentary receipt-not-found responses preserve the original key. If reload loses the original submitted values, the client can reconcile by that key but cannot reconstruct a write from current values or newly typed data. Draft editing/review does not authorize another write. Refresh/discard never clears an unresolved key, merges values, retries automatically or generates a replacement key.

An Applicant correction confirmed by the Server is no longer an unsaved draft only when the current fields still match that operation's exact frozen request. Editing different values or reconciling an orphan key does not mark another draft as saved. Explicit completion retains compare-before-clear metadata checks, then starts the next task through a fresh `/application` document. This prevents a completed correction's old baseline or delayed background refresh from disabling the following action. Unsubmitted and UNKNOWN work keeps its existing dirty/key protection; completion is not an automatic stale-draft refresh.

A completed receipt from another tab does not permit automatic source adoption over this page's unsaved draft. The confirmed view explicitly preserves that distinction. Acknowledging that completed operation compares and clears only its resolved key, then returns to the retained draft without document navigation. Cancelled, failed or malformed refresh keeps that draft; only explicit discard confirmation and a successful authorised matching read replace it. An unresolved UNKNOWN key still cannot be cleared or replaced through this path. The fresh-document completion above remains appropriate when this page has no unsaved work.

Native HTTP/D1, held-batch and browser evidence belongs to #98/#101/#106 with exact source attribution. Mixed-version deployment/draining/rollback, independent review, Owner acceptance and release remain separate gates; this ADR authorizes none of them.
